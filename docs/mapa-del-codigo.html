1. La idea en una página

La app son dos programas que nunca se hablan directo. Entre los dos hay un solo archivo, data/daily.json, que es como un diario impreso: uno lo escribe y el otro lo lee.

La pregunta que resuelve la mitad de los problemas

Cuando algo se ve mal, pregúntate primero de qué lado está. Abre data/daily.json en GitHub (o mira la hora "Actualizado hoy HH:MM" arriba en la app):

  • Si el dato ya está mal o viejo en el JSON, el problema está en el recolector (Python, GitHub Actions).
  • Si el JSON está bien pero la app lo muestra mal, el problema está en el visor (React, Vercel).
  • Si el JSON está bien y es nuevo, pero la app muestra uno viejo, el problema está en el deploy de Vercel.

Por qué está hecho así (y no "la app pide los precios cuando la abres")

  • $0/mes: pedir precios en vivo desde el navegador exige una API pagada. Así, cada fuente se consulta una vez por hora desde GitHub, dentro de los planes gratis.
  • Abre al instante: el visor nunca espera a una API; todo viene pegado adentro.
  • Si una fuente se cae, la app no se cae: se queda con el último dato bueno ("degradar, no caer", sección 11).
  • Historial gratis: cada versión del JSON queda guardada en git; puedes ver qué mostraba la app cualquier día.

El costo: el precio nunca es "en vivo". Tiene hasta ~1 hora de antigüedad, o más si GitHub atrasa los cron. Por eso difiere un poco de Yahoo Finance: no es un error, es antigüedad.

El problema conocido: GitHub atrasa o bota los cron

Cuando GitHub está cargado, a veces no dispara los schedule, o los dispara 20-40 minutos tarde. No es un bug del repo: los runs que sí llegan terminan bien. Síntoma típico: huecos de varias horas sin commits "precios: …". Es el punto 2 del CLAUDE.md. La solución de respaldo quedó preparada pero sin armar: cron-job.org + un token tuyo.

Botón manual: en GitHub, pestaña Actions → "Recolector (cada hora)" → Run workflow. Corre al tiro, sin esperar al cron. Sirve para probar si algo se arregló.

5. El corazón, paso a paso

collector/main.py: la función main() (línea ~313)

  1. Carga llaves y watchlist (cargar_env, parse_watchlist). Imprime qué llaves detectó: es lo primero que conviene mirar en el log. Sin FINNHUB_KEY se detiene aquí, sin error.
  2. Precios: actualizar_precios (~34). Por cada ticker: si es nuevo, siembra historia desde Yahoo; después pide el precio a Finnhub y guarda el punto.
  3. Noticias: noticias.recolectar_bloques(), que devuelve Mundo, Chile, Actualidad y la lista de errores.
  4. Referencias: actualizar_referencias (~261). Banco Central + VOO/QQQ/VTI. Si una serie falla, se queda con el valor anterior y lo anota al pie de la app (ver sección 11).
  5. Posiciones: construir_posiciones (~191). Por cada ticker: fundamentales EDGAR, segmentos, métricas avanzadas, noticias del ticker y revisión de tesis.
  6. Escribe data/daily.json (actualizar_daily_json, ~292).
  7. Alertas ±5% y resumen de la mañana, cada uno dentro de un try: si fallan, se imprime el error y la corrida sigue. Van al final a propósito: avisan exactamente lo que vas a ver en la app.
Cómo leer el log de un run

Cada paso imprime una línea con título: Actualizando precios..., Leyendo noticias..., Actualizando referencias..., Revisando movimientos fuertes..., Resumen de la mañana.... Si el run se cae, la última línea con título antes del error te dice en qué paso fue. Las líneas aviso: y no se pudo son fallas parciales que no detuvieron nada.

.github/workflows/daily.yml: el envoltorio en GitHub

  1. checkout + setup-python: baja el repo y prepara Python 3.12.
  2. frescura (línea ~38): si daily.json tiene menos de 45 minutos, escribe correr=no y los pasos siguientes se saltan. El botón manual fuerza correr=si.
  3. pip install: instala las librerías de collector/requirements.txt.
  4. python collector/main.py, con todas las llaves inyectadas desde Secrets.
  5. push con reintentos (línea ~93): guarda aparte los archivos recién generados, se pone al día con GitHub, los vuelve a copiar encima, fusiona tesis.json (nunca lo pisa) y hace commit + push. Si otro run se adelantó, reintenta hasta 3 veces.

En la pestaña Actions, cada uno de estos pasos aparece con su propio ✓ o ✗. El paso con ✗ te dice dónde buscar.

8. Las llaves (secrets): qué se rompe si falta cada una

Viven en dos lugares distintos, y eso importa al debuggear: las del recolector están en GitHub → Settings → Secrets and variables → Actions; las de las funciones que escriben, en Vercel → Project → Settings → Environment Variables. En tu PC hay una copia local en el archivo .env (no se sube al repo).

Los tokens de GitHub vencen

Los "fine-grained tokens" tienen fecha de expiración. Si un día no puedes guardar nada desde la app y antes sí podías, lo primero es revisar si venció el token (GitHub → Settings → Developer settings → Fine-grained tokens).

9. Guía de síntomas: "veo X → mira acá"

Ordenados de lo más común a lo menos. Cada uno dice qué revisar primero, sin tocar código.

La app muestra precios de hace horas ("Actualizado hoy" con hora vieja)

  1. GitHub → Actions → "Recolector (cada hora)". ¿Hay runs en las últimas horas?
    → No hay runs: GitHub está botando los cron (sección 3). Aprieta Run workflow para salir del paso.
    → Hay runs en rojo: abre el último y mira qué paso tiene ✗ (sección 5).
    → Hay runs verdes: sigue al punto 2.
  2. ¿Hay un commit "precios: …" reciente en el repo? Si lo hay, el problema es Vercel: revisa en Deployments si el último deploy falló.

Run en rojo en Actions

  1. ✗ en "frescura": error del script que decide si correr (muy raro).
  2. ✗ en "pip install": falló la instalación de una librería. Suele ser pasajero; vuelve a correrlo.
  3. ✗ en "python collector/main.py": error de código o de una API. Busca la última línea con título en el log, y abajo verás Traceback con el archivo y la línea exactos.
  4. ✗ en el push: chocó con otro run que subió al mismo tiempo, tres veces seguidas. Casi siempre se arregla solo en la siguiente hora.

Una acción aparece como "pendiente" o no aparece

  1. Mira el pie de la app: "Finnhub: sin precio nuevo de X" significa que Finnhub no la tiene o respondió error (sources/prices.py).
  2. El plan gratis de Finnhub solo cubre bolsas de EE.UU. Una acción extranjera se agrega por su ADR (ej. BYD: no 002594 de Shenzhen, sino BYDDY). Para clases de acción se usa punto: BRK.B.

Una card sin fundamentales, o con campos vacíos

  1. Mira el log: TICKER: fundamentales no se pudieron actualizar apunta a EDGAR, o a SEC_USER_AGENT si es 403.
  2. Algunos campos vacíos son a propósito: la empresa no reporta ese dato en XBRL (por ejemplo, el EPS de BRK.B). Se deja vacío en vez de mostrar un dato viejo (edgar.py, TAGS).
  3. Empresas extranjeras (SQM, Toyota…) no reportan a la SEC: nunca tendrán fundamentales.

Noticias sin resumen, o con el titular repetido como resumen

  1. Gemini falló o se acabó la cuota gratis del día; se usa el respaldo por palabras (sources/gemini.py).
  2. Con Reuters es un problema conocido: su feed (vía Google News) no trae texto, solo el titular.

Se cuela un tema que no quieres (deportes), o un medio llena todo

  1. Las perillas están arriba de collector/noticias.py: PALABRAS_DEPORTES (agrega la palabra que se cuela) y MAX_POR_MEDIO.
  2. La lista de medios está en collector/sources/feeds.py.

UF, dólar, PIB o desempleo no cambian en días

  1. El recolector conserva el valor anterior cuando una serie falla, y lo anota al pie de la app ("Banco Central: sin dato nuevo de uf…"). Si no hay nada al pie, la serie sí se actualizó.
  2. PIB (trimestral) y desempleo (con ~2 meses de rezago) cambian poco a propósito: mira su período ("T2 2026", "may–jul 2026").

No me llegó el resumen de la mañana

  1. Sale solo si hubo un run del recolector entre las 07:00 y 12:00 de Chile. Si GitHub no corrió en esa ventana, no sale (sección 3).
  2. Para forzarlo: Actions → "Resumen por Telegram (manual)" → Run workflow.

Me llega la "misma" alerta de nuevo

  1. Mira la fecha. Una alerta por día de Nueva York es lo normal: dos días seguidos con −5% son dos alertas reales (pasó con INTC el 28 y el 29 de septiembre).
  2. El mismo día solo repite si se movió otro 5% o cambió de signo. Estado en data/alertas_enviadas.json.

No puedo guardar desde la app (watchlist, tesis, simulador)

  1. Abre la consola del navegador (F12 → Console/Network) y mira el código: 401 clave mal escrita, 500 falta configurar algo en Vercel, 502 GitHub rechazó (casi siempre un token vencido).
  2. Vercel → tu proyecto → Logs muestra el error de la función.

El Radar está viejo o vacío

  1. Corre solo los lunes (06:23 UTC). Si GitHub botó ese run, se queda con la semana anterior: Actions → "Radar (semanal)" → Run workflow.

Mi portafolio de Fintual no aparece

  1. Es esperable: Fintual deprecó su API (lo confirmó su soporte el 14 de agosto). No es un error nuestro. No perder tiempo reintentando.

11. Cinco ideas que se repiten en todo el código

Si entiendes estas cinco, puedes abrir casi cualquier archivo y entender por qué está escrito así.

1 · Degradar, no caer

Si una fuente falla, se usa el último dato bueno y se sigue (_obtener_fundamentales, actualizar_referencias…). Así un problema con la SEC no te deja sin precios. La contracara: un dato puede quedar congelado. Por eso cada falla parcial (Banco Central, EDGAR, Finnhub, Gemini, feeds) queda anotada en errores y se ve al pie de la app: si ves líneas ahí, ese dato es viejo.

2 · Nunca inventar

Si no hay dato, el campo queda vacío o "pendiente", nunca con un valor supuesto. Ejemplos: el PIB no muestra variación si falta el trimestre de hace un año; Gemini descarta una cifra si su cita no aparece textual en el documento.

3 · Un aviso nunca tumba la corrida

Telegram, alertas y resumen van dentro de try: si fallan, se anota y el snapshot igual se sube.

4 · Verificar contra la fuente real

Cada código de serie, feed o tag de la SEC se probó contra la API de verdad antes de usarlo, y el comentario suele decir cómo. Cuando un comentario dice "encontrado de verdad en una corrida real", es un bug que ya pasó una vez.

5 · Los comentarios explican el por qué

El código dice qué hace; los comentarios (# en Python, // en TypeScript) y los textos entre """ al inicio de cada función explican por qué se hizo así y qué error evita. Para entender una función, lee primero su docstring. El CLAUDE.md de la raíz es la bitácora de decisiones: qué se decidió, cuándo y por qué.

Las reglas duras (en CLAUDE.md)

  • $0/mes: nada pagado sin preguntar antes.
  • El Radar no aconseja: muestra datos, nunca "deberías comprar". Por eso no hay puntaje agregado.
  • Copyright: las noticias se reescriben, 1-2 frases, siempre con link.
  • El color es solo señal: verde, ámbar, rojo y acento solo para estado.
  • Las tesis son inmutables: editar significa cerrar una y abrir otra.
